# DECISIONS_LOG.md
1. **Idempotency Recovery:** Abandoned leases require reconciliation to verify commit status; no blind retries.
2. **Reserve Loss Allocation:** SME reserve does not absorb ordinary credit defaults on non-recourse sales.
3. **Ledger Protection:** Strict `BEFORE INSERT/UPDATE/DELETE` triggers ensure `POSTED` journals and lines are mathematically immutable.
4. **Implementation Foundation:** Docker, CI, and Flyway are mandatory prerequisites in Milestone 1 to ensure a stable development environment.
5. **No-Lombok Core Entities:** Core domain entities use explicit getters, setters, and constructors rather than Lombok annotation processing to guarantee compiler portability across Java 21 LTS and diverse build environments.
6. **Flyway Role Portability:** Migration `V4__enable_rls_foundation.sql` includes an idempotent role check ensuring the `app_worker` role exists when running against clean ephemeral databases (CI / Testcontainers).
7. **Safe UUID Casting in RLS Policies:** RLS policies wrap `current_setting('app.tenant_id', true)` with `NULLIF(..., '')::uuid` to prevent invalid UUID syntax exceptions when context is unset or empty.
8. **Stateless Token Management:** Frontend retains authentication state via Angular Signals and sessionStorage, avoiding long-term localStorage exposure to mitigate persistent token theft.
9. **Elimination of Public Admin Registration:** Public self-service registration is strictly limited to SMEs. Registration payloads cannot specify privileged organization types or roles; initial administrators are provisioned via `V5__seed_platform_admin.sql`.
10. **Aspect-Driven Transactional RLS Binding:** `TenantRlsAspect` runs at `@Order(200)` inside Spring `@Transactional` boundaries (`@Order(100)`), ensuring PostgreSQL `app.tenant_id` is set on the active transaction connection and auto-cleared upon commit/rollback (`is_local=true`).
11. **Elimination of Blanket Permissive RLS Policies:** Blanket `USING (true)` policies on `users` and `user_organizations` were eliminated. Pre-authentication lookups and atomic SME registration are handled via `SECURITY DEFINER` functions with fixed `search_path`, preserving strict table-level RLS without granting `app_worker` bypass privileges.
12. **Lockfile Tracking:** `package-lock.json` was un-ignored from version control and committed to ensure reproducible dependency installs with `npm ci` in Docker and CI workflows.
13. **Direct Buyer Demographics on Invoices (D1 Option A):** Buyer legal name, GSTIN (15-character), and optional PAN (10-character) are captured directly on the `invoices` table to support ad-hoc and un-onboarded buyers without forcing upfront buyer registration.
14. **Global Document SHA-256 Uniqueness (D2 Option A):** Enforce non-partial platform-wide cryptographic uniqueness across all document records via `uq_global_document_sha256` to definitively eliminate double-factoring and duplicate collateral fraud across tenants.
15. **Local Persistent Document Storage (D3 Option A):** `DocumentStorageService` stores files outside the web root on a dedicated filesystem volume (`/var/app/documents`), with stream-to-staging SHA-256 calculation, magic-byte `%PDF-` validation, bounded size limits (10MB), atomic rename into tenant storage, and transaction rollback synchronization.
16. **Explicit SME Submission Workflow (D4 Option A):** Invoices remain in `DRAFT` status upon PDF upload. An explicit SME action (`POST /api/v1/invoices/{id}/submit`) is required to validate document presence and transition status to `PENDING_VERIFICATION`.
17. **Two-Phase Idempotency with Fencing Tokens:** `idempotency_keys` uses monotonic `fencing_token UUID` acquired in Phase 1 (`REQUIRES_NEW`), validated in Phase 2 with `SELECT ... FOR UPDATE` before business mutations; the row lock is held until transaction commit or rollback to eliminate race conditions during expired lease reclamation.
18. **Composite Foreign Key Tenant Consistency:** `(created_by, sme_org_id)` and `(uploaded_by, sme_org_id)` reference `user_organizations(user_id, org_id) ON DELETE RESTRICT` to guarantee that invoice creators and document uploaders belong to the active SME tenant and cannot be cascade-deleted.
19. **Dual Buyer Access Model (D2-1):** High-entropy cryptographic token links (`#token=...`) serve ad-hoc un-onboarded buyers without requiring upfront user provisioning, while authenticated portal buyers authenticate against verified `organization_tax_profiles` matched by GSTIN.
20. **Strict Confirmation Outcome Recording (D2-2):** Buyer confirmation transitions invoice status to `VERIFIED` and sets `verified_confirmation_id`. Rejections or disputes transition invoice status to `REJECTED`, record `last_buyer_response_id`, and capture immutable canonical evidence without mutating other invoice parameters.
21. **Seven-Day Confirmation Request Expiry (D2-3):** Confirmation requests expire 7 days after issuance. The sweeper uses `SKIP LOCKED` and atomically transitions overdue requests to `EXPIRED` while revoking all active child sessions.
22. **Universal Lock Hierarchy (D2-8):** All mutation paths strictly follow the lock hierarchy: `invoices` -> `buyer_confirmation_requests` -> `buyer_confirmation_sessions` (deterministic `id ASC`), eliminating deadlock risks across response submission, replay, token exchange, and sweeper execution.
23. **Session-Level Idempotency Leases & Monotonic Fencing (D2-5):** Leases and `fencing_generation` counters are stored directly on `buyer_confirmation_sessions`, tightly coupling idempotency to the session lifecycle without requiring unauthenticated callers to hold records in `user_organizations`.
24. **RFC 8785 Canonical JSON Serialization (D2-6):** Authoritative legal evidence payloads are serialized on the server into RFC 8785 canonical JSON format (lexicographical Unicode code-point order, canonical numeric format, SHA-256 digest) ensuring non-repudiation.
25. **AES-256-GCM Encrypted Outbox (D2-7):** Outbox notifications are encrypted at rest using AES-256-GCM with 12-byte IV, AAD binding (`aggregateType:aggregateId:tenantId:keyVersion`), and key rotation support to safeguard PII and secure token links.
26. **Dedicated Security Definer Role Isolation:** `buyer_confirmation_definer` is a `NOLOGIN` role owning authoritative state transition procedures, preventing runtime `app_worker` from directly updating sensitive invoice verification columns.
